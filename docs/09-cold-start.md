# 冷启动与唤醒

前面几页讲的四层保活，全部跑在服务器内部。实例一旦被平台休眠、关机或回收，Windows 里的计划任务、看门狗、隧道进程统统不在，公网看到的只有超时。此时唯一的出路是让平台把实例拉起来，也就是本页说的「唤醒」。

## 先分清三种不可达

公网 `health` 失败只说明「不通」，不说明原因。按下面三行分流，别在错误的方向上折腾。

| 现象 | 怎么确认 | 处置 |
|---|---|---|
| 隧道地址失效 | 公网请求返回 `404`，页面是隧道服务商的错误页；机器本身还活着 | 取新地址，或改用固定域名隧道（见下文） |
| 实例被休眠 / 关机 | 厂商客户端或控制台显示「已休眠 / 已关机」，状态不是运行中 | 用客户端点一次「连接 / 开机」，等桌面可交互 |
| 网关或服务停了 | 客户端能进桌面，但本机 `health` 依然失败 | 进桌面看计划任务状态与 `setup.log` |

判据顺序建议：先看隧道错误页（一眼就能认出是隧道服务商的英文错误页），再看客户端里的实例状态，最后才怀疑网关。三者都正常时才需要翻审计日志。

## 唤醒由平台发起，不由服务器发起

要点只有三条：

1. **唤醒是平台侧动作。** 休眠实例被恢复时通常接着上次的会话；关机实例则是重新开机，之前的进程一个都不在。
2. **触发方式只有厂商通路。** 桌面客户端、网页端，或控制台里的实例操作。没有第二种入口。
3. **本方案不调用未公开接口，因此不做「自动开机」。** 这是有意的设计取舍，不是能力缺失。任何声称能绕过厂商通路冷启动的方案，要么依赖未公开接口，要么依赖平台恰好有开放 API。

如果你确实需要无人值守的自动开机，正确做法是走平台提供的正式接口并申请相应权限，而不是在本项目里加钩子。

## 唤醒之后要做三件事

点完「连接」不等于恢复完成，顺序别跳：

1. **等桌面真正可交互。** 看到桌面、能点开开始菜单才算就绪。客户端显示「正在启动中」时，`health` 一定还是失败。
2. **重新确认隧道地址。** 免费隧道每次启动会换域名，旧地址会一直返回隧道服务商的错误页。取到新地址后同步到本机配置。
3. **本机连续三次 `health` 通过再收工。** 单次成功可能是缓存或刚好撞上重启窗口。

```bash
# [本机] 连续探测，三次都 ok 才算恢复
for i in 1 2 3; do python3 client/bridge.py health >/dev/null && echo "ok $i" || echo "fail $i"; sleep 5; done
```

## 让隧道地址不再漂移

地址漂移是「机器明明在跑、就是连不上」的最常见原因，比实例休眠更常见。按稳定性排序：

| 做法 | 地址是否固定 | 代价 |
|---|---|---|
| cloudflared + 自有域名 | 固定 | 需要一个域名，首次配置稍长 |
| 自建反向代理 + 固定 IP / DDNS | 固定 | 需要一台有公网入口的机器 |
| ngrok 付费固定域名 | 固定 | 按月付费 |
| ngrok 免费版 | **每次启动都变** | 免费，但每次重启都要重新取地址并同步客户端 |

用免费版时的现实预期：重启后必须有人或脚本把新地址同步给客户端。可以把新地址写到固定的中转位置（对象存储的一个文本对象、你自己的一个静态页面），客户端启动时先读它再发请求。这仍然需要一次「取地址」的动作，只是把它自动化了。

## 客户端侧兜底

服务器内部的自愈解决不了「整机不在」。客户端这边能做的只有两件事：

- **定时探测 + 明确告警。** 连续失败 N 次（建议 3 次、间隔 5 分钟）后告警，告警文案要写清下一步动作：「去厂商客户端点一次连接」，而不是只报 `down`。
- **不要把控制面当永久在线服务。** 长任务写检查点、结果先落盘再读，不要依赖进程长期存活。机器随时可能被回收，这是平台策略，不是故障。

## 这一页的边界

- 不能阻止平台休眠、关机、回收实例，也不能缩短平台侧的启动耗时。
- 不能在没有厂商登录态的情况下唤醒实例。
- 不能保证免费隧道域名不变。
- 唤醒成功不等于业务恢复：原有 Web 服务、数据库连接等仍需自行确认。
